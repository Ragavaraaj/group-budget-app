# Auth: Google sign-in

Code: `apps/server/src/modules/auth` (server), `apps/web/src/auth` and `apps/web/src/features/auth` (client).

**Flow** (server-side authorization code + PKCE, using `arctic`, which needs only `fetch` and Web Crypto; it bundles into the Worker and runs under `workerd` in the test suite. The round trip to Google itself is mocked in tests and **not yet exercised against real Google**; no third-party JavaScript in the page, so the CSP stays strict):

1. `Continue with Google` → full-page navigation to `GET /api/auth/google/start` (optionally carrying an invite token, and, in the installed app, an attempt hash).
2. The Worker creates `state` + a PKCE verifier and stores them in **D1** (`oauth_states`, 10 minutes, single use; **one write**, since this endpoint is open to anyone: expired rows are swept when a sign-in completes and on about one start in fifty), sets a short-lived HttpOnly cookie holding the `state`, and redirects to Google with scopes `openid email profile` and `prompt=select_account` (phones get shared, so always ask which account).
3. Google → `GET /api/auth/google/callback?code&state`. The Worker consumes the stored state (a replayed callback finds nothing), exchanges the code, checks the ID token's **issuer, audience, expiry and `email_verified`** (the token comes straight from Google's token endpoint over TLS, so as the code flow allows it is not signature-checked), and applies the **sign-up gate** below.
4. Upsert the user by Google `sub` (never by email; emails can change), create the personal group with its default categories on first sign-in, refresh the display name and photo (and let group-mates' devices know, since names travel on membership rows), create a session, set the cookie, redirect to `/` (or to `/join/<token>` when the sign-in began from an invite).

**The cookie proves "same browser".** If the callback arrives without the `state` cookie, sign-in did not finish in the browser that started it. That is legitimate only for the installed-app hand-off below; otherwise it is refused (`invalid_state`), because it could be someone steering a victim into signing in as the attacker.

**Sessions**: random 256-bit token; only its SHA-256 hash is stored in D1; cookie `gb_session`, `HttpOnly; SameSite=Lax`, `Secure` in production (plain http on localhost in development); 30-day sliding expiry. To stay inside D1's write quota, expiry is only **extended when less than half of it remains** (and the cookie is refreshed then), not on every request. Logout revokes the session and needs a connection.

**Sign-up gate** (default; the app is not open to the world): a Google account may _create_ an account only if its email is in the `ALLOWED_EMAILS` setting (you, to bootstrap) **or** it arrives with a valid, unexpired, not-used-up group **invite token**. Existing users always sign in. This means a friend you invite to a group can join without you touching the server. The login page explains the refusal ("ask a group owner for an invite link").

**What you need to set up in Google Cloud Console** (needed before anyone can sign in on the deployed app; localhost works for development with the dev stand-in below):

1. Create a project → _Google Auth Platform_ → configure the consent screen (External).
2. Scopes: only `openid`, `email`, `profile` (non-sensitive; no Google verification needed).
3. **Set publishing status to "In production".** In "Testing" the app is capped at 100 test users and consent expires after 7 days ([Google docs](https://support.google.com/cloud/answer/15549945)).
4. Create an OAuth client ID (type _Web application_). Authorized redirect URIs: `http://localhost:5173/api/auth/google/callback` (dev, through the Vite proxy, which keeps the original host) and `https://group-budget.<your-subdomain>.workers.dev/api/auth/google/callback` (the free Cloudflare address). When you buy a domain, add `https://<your-domain>/api/auth/google/callback` too. Google rejects bare IPs and non-public hostnames. The redirect URI is built from the request's own origin, so no setting is needed for it.
5. Store the credentials as Worker **secrets**: `wrangler secret put GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `ALLOWED_EMAILS` (a comma-separated list), or add them as type _Secret_ in the dashboard. They must be secrets, not plain variables: a `wrangler deploy` (which the CI deploy job runs) overwrites plain variables that were set in the dashboard, but never deletes secrets. Locally they go in the gitignored `apps/server/.dev.vars`. Never in git.

**Known risk — installed iOS web app (the group uses iPhones, and installs the app from Chrome).** Every iOS browser, Chrome included, runs on Apple's WebKit. A home-screen web app, whether added from Chrome or Safari, gets its own cookies and storage, separate from the browser's tabs, and reports conflict on where a third-party OAuth redirect ends up: the app window, an in-app browser sheet, or the browser ([example thread](https://developer.apple.com/forums/thread/649699), [PocketBase discussion](https://github.com/pocketbase/pocketbase/discussions/2429)). If it ends up outside the app, the user signs in there but the installed app stays signed out. We can't control that, so sign-in is designed **not to depend on where the redirect lands**.

**Attempt-login (used only in standalone mode: `navigator.standalone` or `display-mode: standalone`; browser tabs, Android and desktop use the plain redirect above).** Like a TV sign-in, the installed app collects its own login:

1. The app creates a random 256-bit `attempt_secret`, keeps it in its own `localStorage` (it survives the app being backgrounded while the user is in the sign-in sheet; storage is per installed app on iOS), and starts sign-in with `GET /api/auth/google/start?attempt=<sha256(secret)>`. The `oauth_states` row remembers the hash.
2. Google sign-in completes wherever iOS puts it. If the callback arrives **with** the state cookie (the app window itself), it signs in normally.
3. Otherwise, after the sign-up gate passes, the callback binds the user to the attempt (`login_attempts`, 5 minutes) and shows a **confirmation page**: "Finish signing in on your installed app? Continue only if you just tapped Sign in there." Pressing Continue (a form POST, subject to the CSRF origin check) marks the attempt confirmed. The page exists so a friend can't be tricked into approving someone else's attempt. It is served with a locked-down CSP (no scripts) and the same `Referrer-Policy` as everything else; with `no-referrer` a browser sends `Origin: null` on this form post and the CSRF check would refuse it, a bug the end-to-end test caught.
4. While the login screen is open the app polls `POST /api/auth/attempt/redeem` every 2 s (only while visible, and immediately when it comes back to the front, for up to 10 minutes). The server hashes the posted secret, finds a confirmed, unexpired, unconsumed attempt, consumes it (a conditional update, so exactly one caller wins) and sets the session cookie in the app's own storage. The secret never leaves the device, so the hash that travelled through the browser is useless. **If the person arrived through an invite link, the invite travels with the attempt** (`login_attempts.invite_token`) and comes back in the redeem response, so the app opens the join page instead of dropping a new person on an empty ledger.
5. Rate-limit `redeem` at Cloudflare ([Security](security.md)): not done in code yet. A typed one-time code is **not** built; add it only if real devices show the polling path failing.

This is tested on desktop with two Playwright browser contexts (separate cookie jars) standing in for the installed app and the browser, including the case where the app is left waiting until the person confirms. What still needs a real iPhone is a confirmation run (in M1b), **using Chrome's "Add to Home Screen"**, to check the hand-back feels right. It is no longer a go/no-go spike. The Google Identity Services ID-token flow is not used: it needs third-party JavaScript, which breaks the strict CSP ([Security](security.md)).

**Not-installed guard.** In a plain iOS Chrome tab, service workers may be unavailable and WebKit caps script-writable storage at 7 days for sites that aren't installed ([MagicBell](https://www.magicbell.com/blog/offline-first-pwas-service-worker-caching-strategies)), which could wipe an unsynced outbox. On a phone outside the installed app the shell shows an "Install this app to your home screen" banner (dismissible for the session), Settings warns when changes have waited over a day, and sign-out warns before discarding unsynced changes. The group is told to install from Chrome (Share/menu → Add to Home Screen); installed web apps are exempt from the 7-day cap.

**Startup and offline.** The last signed-in person is cached in `localStorage`, so the app opens offline straight into their local data. If the server says the session ended, the app keeps working with a banner and the sync queue waits; the login screen then offers sign-in again.

**Dev/test only**: a stand-in for Google and a one-step sign-in exist only when `ENVIRONMENT` is not `production` **and** `ENABLE_DEV_LOGIN=1`. `ENVIRONMENT` defaults to `production`, so they can't be on by accident in a deployed Worker (a test asserts it is off even if the flag is set). With dev login on and no Google credentials, "Continue with Google" leads to a small page where you type any email, then runs through the **same callback code** (state, sign-up gate, attempt-login, confirmation), so the real flow is testable without Google. `POST /api/auth/dev-login` signs in directly (used by the end-to-end tests; it bypasses the gate).
