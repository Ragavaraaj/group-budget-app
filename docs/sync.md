# Sync protocol

Why custom: expenses are append-mostly, edits are rare and rarely concurrent, so last-writer-wins at row level is acceptable and a CRDT is overkill. Code: `apps/web/src/{db,sync}` (client), `apps/server/src/modules/sync` (server).

**Client**

- The UI reads only from the local database (Dexie, one IndexedDB database per signed-in person: `budget-<userId>`), through live queries. Tables: `groups`, `members`, `categories`, `expenses`, `settlements`, `budgets`, `recurring`, `outbox`, `meta` (the pull cursor, pending backfills, recent rejections, the month start day). Budgets and recurring rules arrived later as a second Dexie version that adds those tables and **clears the pull cursor once**: a device still running the older code until it was reloaded may have pulled past budgets, rules and member fields it didn't know how to keep, and a cursor already ahead of them would never bring them back. The next sync is one full pull; nothing else on the device is touched.
- Every write goes through `db/repo.ts`: it changes the local row **and** appends a mutation to the `outbox` in one transaction, so the screen updates at once and nothing can be lost between "saved" and "queued". A mutation is `{mutationId, entity, op: upsert|delete|restore, baseVersion, data}`. Consecutive queued edits of one row chain their `baseVersion` (3, then 4, then 5), so the server doesn't call the later ones stale.
- **Flush triggers**: app start, the `online` event, the tab becoming visible, right after each local write, and the polling timer. (Background Sync is not used: iOS lacks it, so foreground triggers are the mechanism.) A sync cycle is: **push** the outbox, **pull** until caught up, then run any **backfills**. Triggers that arrive mid-cycle are coalesced into one more cycle. **A push the server cannot take (a 5xx, say) does not stop the pull and the backfills**: a group someone has just joined reaches the device only by pulling, so one stuck change at the head of the queue would otherwise keep it off the phone for ever. The failure is still reported when the cycle ends. A lost session or lost network does stop the cycle, since the pull would fail the same way. **When a cycle fails, the engine keeps where and why** (`failure`: the step, such as "sending changes", "receiving changes" or "loading a group", and the HTTP status and code or the error's name and message; if a failed push was followed by a failed pull, both are kept, the second as `also`). It is cleared as soon as the state is anything but an error. Settings shows it under the Sync card, so "Sync problem" on a phone can be told apart without a debugger. The full errors go to the console, once while the same failure repeats. `caughtUp` says the last cycle received everything the server had, every page of the pull and every group backfill; it stays true when only sending failed. The join page opens a group only when the sync has caught up **and** the group's row is there, because the row can be written by the first page of a pull or backfill before a later page fails.
- **Push** sends the outbox oldest first in requests of at most **10** mutations. A rejected change is dropped from the queue and recorded (Settings shows "Changes the server didn't accept"), **and undone locally** so this device keeps agreeing with the server and every other device: a new row the server never accepted (version 0) is removed from the local database (and so from totals, balances and exports), and a row the server does hold goes back to the server's version by re-fetching its group (the backfill mechanism below). The person is told in both cases. If the server refuses a whole request as malformed, the engine retries the changes one at a time to find the culprit, so one bad change can never block the queue. If a request is answered with nothing at all, the cycle stops with an error rather than re-sending forever.
- **Pull by polling**: about every 30 s while the app is visible and online, backing off (doubling) to 5 minutes while nothing changes, going back to 30 s on news, and **stopping while hidden**. A poll with no news is one batched read of a few indexed lookups. **While the live connection is up** (below) polling only runs at the slowest interval, as a safety net. After a 401 the engine stops polling and the app keeps working from local data; the queue waits for a new sign-in.
- **Applying pulled rows**: a row the device has unsent edits for is left alone (its own change will be sent, and the server's version comes back afterwards), and a row is never replaced by an older one. A change the server accepted updates the local row's `version` straight away (unless newer edits are queued) so later edits aren't flagged as stale.
- **Local DB is scoped per user**, so two accounts on one device never mix. **Logout** needs a connection, warns if the outbox is non-empty (unsynced changes would be lost), then deletes that user's local database.

**Server**

- `POST /api/sync/push` — array of at most 10 mutations. Flow: **(1) read** the caller's memberships, the rows being changed and anything they reference, **(2) validate and authorize** each mutation in order (a later mutation in the same push sees the effect of an earlier one), **(3) write everything in one `db.batch`**: the sequence reservation, row upserts and tombstones, `audit_log` rows, and one `processed_mutations` insert per accepted mutation. Because `mutation_id` is a primary key, a replay of an already-applied mutation is detected up front and reported as `duplicate`; if two copies race and one batch hits the key, it rolls back whole and the handler re-reads and reports the loser as `duplicate`. **Only that one error is retried** (recognised by SQLite's message naming `processed_mutations`); any other failure is rethrown at once, since a blind retry would repeat about 40 queries and, on the free plan's 50-per-invocation cap, hide the real error behind a quota one. Per-mutation result: `applied (+version, +conflict) | duplicate | rejected(reason)`. Reasons: `not_a_member`, `not_found`, `deleted`, `group_mismatch`, `invalid_reference`, `limit_reached` (a group already holds its 60 budgets or 50 recurring rules; a **restore** counts like a new row, so deleting and restoring can't get past the cap). Budgets and recurring rules go through the same flow; a rule's next due date is worked out by the server as part of the write. An **active** rule may name only people who are in the group now (a template for future expenses must not keep charging someone who left), while old expenses and **paused** rules may still name them, so a member can always pause one. Deleting a rule clears its next due date. An Undo the same day (in India) loses nothing: the rule carries on from the last date it made, as if it had not been deleted. A rule that was gone longer starts again from today, like a resume, so it never revives dates from while it was deleted; either way it goes back no further than the 93-day floor. Inside one push a delete gives its place back, so the group limit is checked against what the push leaves behind (an offline delete followed by Undo, sent together, both apply at the limit). A rule whose creator has left is **taken over** by whoever edits it next. A member removed between steps (1) and (3) could land one write; that window is tiny and every write is audit-logged, so it's accepted.
- The upsert is `INSERT … ON CONFLICT(id) DO UPDATE … WHERE deleted_at IS NULL AND group_id = ?`: last writer wins, but never over a tombstone and never across groups, even if two requests race.
- Why 10: the free plan allows 50 D1 queries per Worker invocation, a push uses about three statements per mutation plus a handful of reads, so 10 stays inside even if every statement is counted separately.
- `GET /api/sync/pull?since=<server_seq>&limit=N[&groupId=…]` — everything changed in the caller's groups since the cursor, oldest first, paged, including tombstones. All reads happen in one D1 batch (one consistent snapshot) and every query is index-served. The tables page independently, so the response cursor is the earliest point every table has been read up to; the rest comes on the next page. The returned cursor is the highest `server_seq` the caller has seen (not the global counter).
- The caller's **own membership rows are always included**, even after removal, so being removed reaches their devices (which then delete that group's data and say so) although they can no longer see the group.
- **Joining a group later**: the group's history has older sequence numbers than the joiner's cursor, so the normal pull would skip it. When a pull shows the person has become a member of a group the device doesn't know (and it isn't the very first sync, which fetches everything anyway), the engine queues a **backfill**: it pulls that one group from `since=0` with `groupId=…`, with its own cursor, resumable after an interruption, leaving the global cursor alone. A backfill for a group you're not in answers 403 and is dropped.

**Live updates (Durable Object hub)**

Polling is the base mechanism and keeps working on its own; the live connection only makes the common case quick.

- The app opens one WebSocket to `/api/live?id=<its own connection id>` while it is visible, online and signed in. The Worker answers that path itself (before the Hono app, because a middleware that rebuilds a response would lose the socket), checks the session cookie and that `Origin` is its own, then hands the connection to a single `LiveHub` Durable Object.
- The hub holds every connected device's socket, tagged by person, using the **hibernation API**: while nothing happens the object is evicted from memory, and the keep-alive `ping` is answered without waking it. It keeps no data and decides nothing; it is told whom to notify.
- After a push commits, the Worker tells the hub which people to notify: the active members of the groups that were written to (already read during the push, so no extra query). It does the same after group changes (create, rename, someone joining, leaving, removed or added back, a hand-over, a deletion; someone just removed is told too) and after the recurring job makes expenses. The call runs after the response (`waitUntil`) and failure is logged and ignored.
- The message is `{"type":"changed"}` and nothing else: no ids, no data. The device answers it by syncing, exactly as if its poll had fired. Each push carries the device's connection id in `X-Live-Id` so the hub **skips the device that made the change** (it pulls right after pushing anyway), while that person's other devices are woken.
- The client gives up on a socket that has not opened within 10 s (a proxy that doesn't pass WebSockets on, like the dev proxy without `ws: true`, would otherwise leave it connecting for minutes), and reconnects with a growing, jittered delay (1 s up to a minute), closes the socket when the app is hidden or offline and reopens it on return (iOS kills background sockets anyway), pings every 30 s and drops a connection that stops answering (a phone that went through a tunnel leaves one that looks open). When the connection comes up the engine syncs once, to pick up what it may have missed; when it goes down while the app is in front it does the same, but not when the app was merely sent to the background (the sync on coming back covers that).
- A person may have 8 connections (tabs or devices); the oldest are closed beyond that, with code 1008. A client closed that way does **not** reconnect by itself (that would evict the next-oldest window, which would come back and evict another, for as long as the windows stay open); it waits for the next wake: the app returning to the front, or the network returning. One hub instance serves everyone, plenty for the 50–100 people this is built for; past that, shard by group.

**Recurring expenses**

A scheduled job (`triggers.crons` in `wrangler.jsonc`, hourly) turns recurring rules that have come due into ordinary expenses, so they appear even if nobody opens the app. It works in small atomic runs because a Worker invocation on the free plan may make only 50 D1 queries: one read finds the due rules (through the `next_due_on` index; a rule whose creator has left the group, or that names someone who has, is held back in the query itself, so it never takes one of the run's places), then **one batch** writes at most 10 occurrences (an expense and an audit row each) and one update per rule that moved on, around 31 statements at most. Every statement for a rule is conditional on the rule still being as the run read it (same `version`, same `next_due_on`, not deleted, active), and the audit row only on the expense having really been written (`changes()`): two overlapping runs, or a run and an edit, change nothing twice, and the loser reports nothing. A rule edited meanwhile is simply picked up again with its new content on the next run. A held rule waits, it doesn't pile up: when someone it involves (its creator, a payer or a person in the split) comes back (reinstated, or rejoined through a link, which sets `joined_at` after the rule's last edit) it carries on from the day they returned, and no run goes back further than the 93-day floor an edit would. Dates at or before the rule's last generated date are never made again, even if an edit planned before a run and committed after it moved the next date back; such a rule is just moved on. A bigger backlog just takes more runs. The new expenses get ordinary `server_seq` numbers, so devices receive them through the normal pull, and the hub tells the group's members.

It is safe to run twice: the expense id is derived from the rule and the date (a version-8 UUID of a hash), so a second insert changes nothing, and each rule's update only applies if the rule is still at the date that run read. "Today" is India's calendar day. A new rule, or a paused one switched on again, never reaches back more than 93 days (and a resumed one starts from today), so a mistyped start date cannot flood a group.

**Conflicts**

- Row-level LWW by server arrival order. **Delete wins over a concurrent edit** (an edit of a tombstoned row is rejected as `deleted`); undoing a delete is an explicit `restore`.
- If `baseVersion` is older than the row's current version, the server still applies the edit but flags `conflict`; the device shows a small "someone else also changed an expense you edited; your version was kept" notice.

**Session expiry while offline**: sessions are long-lived (30 days, sliding). If one expires, the app still opens and works from the local database; the outbox simply waits, with a banner and a "Sign in to sync" status. Signing in again flushes it.

**Safety nets**

- An append-only `audit_log` (mutation id, user, group, entity, before/after JSON, timestamp) is written in the same batch as every applied mutation. `server_seq` alone only gives the _latest_ state of each row, so without this a bad merge or a bug can't be diagnosed or undone.
- D1 Time Travel can restore the whole database to any minute within its retention window ([Infrastructure](infrastructure.md)).
- "Export everything as JSON/CSV" is in Settings (CSV cells that start with `=`, `+`, `-` or `@` are defused so a spreadsheet won't run them).
- Tests cover idempotent and concurrent pushes, delete-vs-edit, authorization, paging across tables, backfill, removal, the recurring job, real WebSockets through the hub, and two real browser contexts end to end ([Testing](testing.md)).
