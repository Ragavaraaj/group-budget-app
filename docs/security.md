# Security

- **Auth**: no passwords exist anywhere in the system. Session tokens are hashed at rest. `state` + PKCE on every OAuth round-trip. See [Auth](auth.md) for the sign-up gate.
- **CSRF**: `SameSite=Lax` + `Origin` header check on all non-GET requests (`middleware/origin-check.ts`; a missing or foreign `Origin` is refused). The API sends the same `Referrer-Policy` as the static files (`strict-origin-when-cross-origin`): Hono's default `no-referrer` makes browsers send `Origin: null` on form posts from the Worker's own HTML pages, which this check would refuse (the sign-in confirmation page; found by an end-to-end test).
- **AuthZ**: membership and role checked per request and per mutation, server-side. Never trust a `group_id` from the client.
- **Rate limiting** on auth, `attempt/redeem` and invite endpoints, done at Cloudflare (rate-limiting rules or the Workers rate-limit binding), **not in Worker memory**: isolates are many and short-lived, so an in-memory counter would not hold. **Not configured yet** (it is dashboard configuration, not code): add rules for `/api/auth/*` and `/api/invites/preview` before real users. This matters most for `GET /api/auth/google/start`, which anyone can call and which writes one D1 row each time (kept to a single write, with occasional sweeping, but a script could still spend the free plan's daily write quota); an edge rule is the control that actually stops that. Invites are random 256-bit tokens, expiring (7 days), usage-limited (20), and stored hashed; the preview endpoint reveals only the group name and inviter to someone who already holds the token.
- **Input**: zod-validate every inbound payload; Drizzle parameterized queries only. Pushes carry at most 10 mutations, and every id list stays under D1's 100-parameter limit.
- **Sessions and tokens**: session, invite, state and attempt tokens are random 256-bit values; only SHA-256 hashes of session and invite tokens are stored (the OAuth `state` is stored hashed, with its PKCE verifier, for ten minutes and single use); comparisons of secrets are constant-time.
- **Exports**: CSV cells that start with `=`, `+`, `-` or `@` are prefixed so a spreadsheet won't run them as formulas.
- **Pages the Worker renders itself** (sign-in confirmation, the dev stand-in) carry a CSP with no scripts and `form-action 'self'`, and escape everything they print.
- **Headers**: strict CSP (`default-src 'self'`, `script-src 'self'`, no inline scripts, no `eval`), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, set by Cloudflare from `apps/web/public/_headers` for the app and by Hono's `secureHeaders` for API responses. `style-src` needs `'unsafe-inline'` because shadcn/sonner inject styles. An e2e test (`e2e/security-headers.spec.ts`) loads the app under the policy the Worker **really serves** and fails on any violation. It already caught one issue: zod 4 compiles validators with `new Function()` at schema-construction time, so `apps/web/src/lib/zod-config.ts` (imported first in `main.tsx`) turns that off rather than allowing `unsafe-eval`.
- **Secrets**: Google client id and secret and `ALLOWED_EMAILS` only as Worker **secrets** (`wrangler secret put`, or type _Secret_ in the dashboard) or the gitignored `.dev.vars`. Plain dashboard variables are overwritten by the next `wrangler deploy`, secrets never are. Config is validated per isolate; the build never contains secrets. Dev login cannot be enabled in production even by setting its flag.
- **No host to harden**: no SSH, firewall or OS patching to do. The Worker runs in Cloudflare's sandbox.
- **Dependencies**: Dependabot on; `npm audit --omit=dev` gates CI. The remaining dev-only advisories (miniflare inside the Workers test pool, esbuild inside drizzle-kit) have no non-breaking fix and never ship; revisit when those tools release updates.
- **The live WebSocket** (`/api/live`): answered by the Worker itself, which checks the session cookie (same lookup as every request) and that the `Origin` header is the app's own before the connection reaches the Durable Object, so another website cannot make a browser open it with the person's cookies (the `SameSite=Lax` cookie is not sent on a cross-site WebSocket either). The hub is reachable only through the Worker's binding. It carries no data: a message is `{"type":"changed"}`, which says only that something changed in a group the person is in; the person's app then pulls through the ordinary authorised endpoint. A person who has just been removed is told once and can learn nothing more. `connect-src 'self'` allows same-origin WebSockets in current Chromium (and is expected to in current WebKit); if a browser blocks it, the app falls back to polling.
- **People without the app** can never sign in: their stored Google id is `placeholder:<id>`, which no Google account has, and the sign-in flow matches only on the id Google returns. They cannot own a group.
- **Deleting a group** needs the owner, and erases the group's records in one batch (no other group is touched; tests check that). **CSV import** reads the file on the device and never sends it anywhere.
- **Backups** (the nightly workflow) hold everyone's data: they go only to a private R2 bucket, are never printed or attached to a run, and the API token that writes them should be the same narrowly scoped one used for deploys. An R2 lifecycle rule should expire old dumps.
